# 检索评测集（块 5）

拿一组**冻结的中文查询**，量两件事：顾客问的商品**有没有出现在前五条里**（Top-5 命中率），
以及**没出现时卡在哪一步**（检索没召回 / 融合没排进前五）。

这是**尺子，不是门禁**。它需要真模型服务、需要索引已经建完、要跑几分钟；塞进
`test:interface` 只会得到一条「要么慢到没人信、要么在缺模型时自己跳过」的绿线。

```bash
npm run eval:retrieval    # 跑评测，报告落在 eval/reports/retrieval-eval-<时间>.json
npm run eval:typecheck    # eval/ 下的 TS 不在任何 workspace 的 tsconfig 里，单独查一遍类型
node eval/generate-queries.cjs   # 重新生成题集（会改写 manifest.json 的 sha256，见下）
```

## 冻结

`queries.validation.json` 是**验证集**：不许边看数字边改它。`manifest.json` 记着它的
sha256，评测第一步就核对 —— 对不上直接判本次作废。改了题就必须重新生成并让 manifest
更新（开发集 `queries.dev.json` 随便改，调参看它）。

题集由 `generate-queries.cjs` 从**真实商品目录**里长出来（种子固定，同一个种子出同一份题），
不手写、不翻译、不猜：

| 类型 | 题面 | 目标（判定为「对」的集合） |
| --- | --- | --- |
| `family` | 品类/款式词（`女士中筒袜`） | **标题命中该词的全部 SPU** —— 一个集合，不是一个 id |
| `color` / `size` | 词 + 颜色/尺码（`有棵树男士内裤 黑色`） | 标题命中该词 **且** 有 SKU 带该颜色/尺码的 SPU |
| `code` | 款式编码（`YAAU1189`） | 该 SPU。只取编码本来就写在标题里的那些，**当量具校准用** |
| `negation` | 词 + `不要黑色` | 不判命中，量**污染率**（前五里还有没有黑色） |

两档，分开报：**窄词**（目标 ≤ 40 条）是主口径，**宽词**（41..120）另算一档 —— 顾客真会打的
名词（`防晒帽`）在目录里天然有几百条命中，混在一起报会把「宽词的容易」平均进窄词。

## 口径与已知边界

* **量的是融合层，不是 HTTP 层。** `POST /retrieval/suggestions` 候选上限 3、每次调用写
  `suggestion_sets` 和审计行、还会叫一次大模型。评测直接调两条腿与 `fuseRecall`（纯读/纯函数），
  不往生产表里写两百条记录，也不把大模型的随机性混进检索读数。因此**候选装配**（去重、
  违禁词拦截、草稿生成）不在本口径内。
* **错品率 = 1 − precision@5**，即前五里不属于目标集的占比。对 `color`/`size` 另报一个更细的
  **同款异色/异码**条数：顾客抱怨最多的是「同一款发错颜色」，和「完全不相干的商品」不是一回事。
* **颜色/尺码题的中位目标集是 1 条**：词已经把范围收窄了，再叠一个颜色往往只剩一个正解。
  这类题的 Top-5 命中天然比 `family` 低，看分时要按类型看，别看总数。
* **尺码维度在这份目录里很薄**：ERP 只给 1,019 个 SKU 填了「规格」，可用的尺码值只有 9 个（`L`/`XL`/
  `165/95` 这类），所以 `size` 只有 9 题。这是目录的事实，不是题集的取舍。
* **索引必须先建完**：评测会核对嵌入覆盖率，< 98% 直接判本次作废 —— 语义腿在索引没建完时是空的，
  那不叫「召回失败」。建索引用 `node scripts/backfill-index.cjs`（见下）。

## 一个真踩到的坑：导入期间的索引会被「封存」

首次导入 14,996 个 SKU 时，**源扫描自己把尝试次数花光了**：状态机对每个切片都返回了「认领才会写」
的那个计数器（`index_attempts + 1`），而它唯一的调用者是源扫描 —— 它每 60 秒（`KNOWLEDGE_SOURCE_POLL_INTERVAL_MS`）
把全表重写一遍，一遍一到两分钟，也就是说它一直在跑。于是每过一遍，每个还没索引的切片就被记一次
尝试，**没有任何一次 provider 调用**。五遍到上限（几分钟的量级，不是几小时），封成 `skipped` ——
那是**终态**，源扫描不会再碰它。代价：18,270 条切片里有 8,489 条（46%）永远没有向量；又因为从未
有过失败，`index_error` 全是 NULL，表里没有任何一行说得清为什么。

顺带记下那条**真实但不是本案**的路径：源扫描的重写会让在途结果按 `discardedAnIndexOutcome` 被丢弃
（它按 `content_hash` 守卫），那条路同样花掉一次尝试而不记原因 —— 但它要求文本在尝试途中真的变了，
而这 46% 的封存节奏与扫描周期对得上，与导入无关。判据在 `knowledge-index-state.spec.ts`：
「不花没人认领的预算」。

已修：状态机只在文本真的变了（`insert`/`reindex`）的时候写索引列；扫描照旧改内容，但不碰
`index_status`/`index_attempts`/`index_error`/`updated_at`（`resetsIndexState`）。

救回来的路（两条，都是 `node` 直跑，别经 npm —— npm 会吞掉 `--flag`）：

1. `node database/scripts/requeue-parked.cjs [--tenant=<id>] [--limit=<n>]`：默认只预览，`--apply`
   才写；只动 `skipped`（唯一回不来的状态，`failed` 自己会被背压重试），清零预算、清空原因，
   并按 `index_error` 分组打印被封存的原因 —— 一片 NULL 就是本案的指纹。
2. `node scripts/backfill-index.cjs`：重建（跑真 `ChunkIndexProcessor.runOnce()`，背靠背调用把吞吐
   从 2 条/秒提到 ~10 条/秒 —— Worker 那两个常量是有意慢的，改它们等于改产品决定）。

**这条值得记进计划书的风险表**：忙导入会把索引封存。现在有操作路径了，但风险没消失 ——
它整个压在一个不变量上：扫描不写索引列。改 `planChunkWrite` 时先看它的规格。
